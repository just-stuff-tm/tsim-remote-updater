# tsim-updater 1.7.11

## Stop a Heltec update that is still sitting in a text

A Heltec update is a text, `UPDATE <url>`, plus a watchdog-only backup of the same command. The T-SIM runs the text straight from the modem. On 1.7.10 that text can still run one wake late, even with eDRX off. If the upload was deleted and replaced, Retry used the old URL, the download 404'd, and the device reported `FAIL: download`.

1.7.11 keeps the 1.7.10 wake path, including the ~22 s text-wake window, and adds a cancel for that stale text plus a short record of when texts showed up.

## Firmware

Version string: `tsim-updater 1.7.11`.

**Text timing (on by default).** Each wake records, and posts it with the usual telemetry as `sd` inside `tl`:

- messages in the modem store (read and unread) at the first inbox pass and at each later pass
- for each text it reads: modem index, network timestamp (SCTS), and milliseconds since this wake
- milliseconds since wake for each `+CMTI`
- wake cause (power, text, gpio6, timer, usb)

Caps are 4 store counts, 4 texts, and 4 `+CMTI` times. The store count is one `AT+CPMS?` per inbox pass (the "SM" used count). Failed parses are omitted. A wake with nothing to report omits `sd`.

**Check before an SMS `UPDATE`.** Before a text `UPDATE` runs, 1.7.11 sends one HTTPS GET to `/api/dev/<id>/updok?url=...` with the same device key the command fetch uses. If the dashboard answers `ok: false`, the T-SIM skips the download, logs the reason, and posts `UPDATE skipped: cancelled on dashboard (<reason>)`. The text is already deleted from the modem, so it will not run on a later wake.

If the check cannot finish (no route on an older dashboard, timeout, any status other than 200, TCP already busy, or the URL does not fit the request), the update runs as it did on 1.7.10. A missing answer never blocks an update. The TLS handshake still has no timer of its own, so a stuck connect can hold this one request.

USB `UPDATE` does not ask. A queued watchdog `UPDATE` does not ask either: the worker drops a cancelled queued command before the device is given it.

## Dashboard

The three Heltec presets, the v1.7.9 modem options, the GPIO6 checkbox, and the v1.7.10 watchdog TTL and stall wording are unchanged.

**Retry of an uploaded file.** Retry checks that the `/fw/<token>` file is still stored. If that token is gone and a current upload has the same sha256, Retry texts the new URL (size, sha256, md5, and token follow the new file). If nothing with that sha256 remains, Retry returns 409: "The uploaded file was deleted. Press Update radio firmware to send the current file." A GitHub release retry still resends the previous URL.

**Deleting an upload.** Every queued `UPDATE` whose URL points at that token is marked cancelled, including the watchdog-only copy, with the error "the uploaded file was deleted". When at least one command was queued, the activity log adds "Cancelled N queued update(s) for the deleted file".

**Cancel update.** The LoRa radio tab shows **Cancel update** beside Retry while a Heltec update is pending, sent, running, retrying, stalled, or failed with Retry still available. Cancel marks every queued Heltec `UPDATE` for that device cancelled (the text's backup and the watchdog copy) and stores a cancel marker (`heltec_cancel`: time, URL, token, command ids). Progress shows cancelled. The activity log says "Update cancelled". A new **Update radio firmware** or **Retry** clears the marker and sends normally. While the marker matches a URL, the command fetch will not hand that queued `UPDATE` to the device, and a failed send will not queue another watchdog copy of it.

`GET /api/dev/<id>/updok?url=` returns `{ok:true}` or `{ok:false, reason}`. `ok` is false when that URL was cancelled after it was sent, or when the upload token is no longer stored. A GitHub `/gh/` link that was not cancelled stays `ok: true`. A missing `url` is HTTP 400, which the firmware treats as "run the update".

**Text line.** The T-SIM tab shows one line when the wake included `sd`, for example `Texts: store 1→2, read #3 sent 13:45:10 at 2.1 s, +CMTI at 9.8 s, wake=text`. The same line is written to the activity log once, when it changes.

## Awake time

The diagnostic does not add a linger and does not change the 1.7.10 text window (about 20 extra seconds on a short text wake, 0 s when the wake already ran past ~22 s). It adds one `AT+CPMS?` on each inbox pass: a short reply in the normal case, and a 3 second give-up if the modem does not answer.

The updok check is one HTTPS GET with an 8 second budget on the reply, and only when the text is an `UPDATE`. Other commands do not call it.

## How cancel works, and older firmware

Cancel does two jobs:

1. Queued copies, including the watchdog backup, are marked cancelled. A device that only runs commands the worker hands it will not install that file.
2. The cancel marker makes `/updok` answer no for that URL. Firmware **1.7.11** asks before it runs a text `UPDATE`, and skips when the answer is no.

Firmware older than 1.7.11 never asks. A text already on the modem still runs on the wake that reads it. Deleting the file turns that URL into a 404, which is the `FAIL: download` seen on 1.7.10. Cancel does not remove a text that has already reached the modem. On 1.7.11, deleting the file also makes `/updok` answer no, so the text is skipped when the check succeeds.

A new Update or Retry after cancel sends a new text and clears the marker, so that new text is allowed.

## Risks

- `AT+CPMS?` can take up to 3 seconds on a pass where the modem does not answer. That time sits in the inbox path that already runs.
- The updok TLS connect has no separate timeout. A hung handshake holds the modem UART until the stack gives up, and only on an SMS `UPDATE`.
- When the check gets no clear "no" (older worker, timeout, any non-200), the text `UPDATE` still runs.
- The timing record keeps four of each item. A busier wake drops the rest.
- The post buffer is larger (reserve 1400 bytes, buffer 4096+2048) so `sd` fits beside a mesh status. A post that still does not fit drops the telemetry tail the same way as before.
